# Модель контенту та контракт із сайтом

Статус: цільовий контракт; приклади нижче не є готовою схемою в коді.

## Типи записів

| Тип | Обов'язковий мінімум | Публічне представлення |
| --- | --- | --- |
| Налаштування сайту | контакти, навігація, глобальні SEO-поля | спільні елементи сторінок |
| Сторінка | ID, шлях, шаблон/тип, поля шаблону, SEO, стан | окрема сторінка |
| Стаття | ID, slug, заголовок, опис, текст, дата, SEO, стан | список і сторінка статті |
| Проєкт | ID, slug, назва, опис, обкладинка, галерея, SEO, стан | список і сторінка проєкту |
| Медіа | ID, шлях, тип, розміри, alt, зв'язки | файл за дозволеним URL |

Стабільний ID не виводиться зі slug. Для редагованих списків кожна картка теж має ID, щоб зміни порядку не сплутували записи. Статус відрізняє чернетку, опублікований запис та архів. Якщо slug змінено після публікації, попередній URL або отримує редирект, або явно фіксується як видалений; це рішення реалізується й тестується, а не лишається випадковою поведінкою.

## Опис поля

Для кожного поля визначаються ключ, тип, назва в адмінці, обов'язковість, межі, підказка, значення за замовчуванням (якщо потрібне) і правила відображення. Типи першої версії: короткий текст, довгий текст, багатий текст у контрольованому форматі, посилання, число, дата, перемикач, зображення, галерея, посилання на інший запис і повторюваний блок. Сервер перевіряє ті самі правила, що бачить редактор. Порожнє значення не підмінюється мовчки текстом розробника.

Приклад смислового контракту:

```text
posts.title: короткий обов'язковий текст
posts.slug: унікальний шлях
posts.cover: зображення з alt
posts.body: довгий текст
projects.gallery: впорядкований список медіа
pages.home.hero.title: короткий текст із рекомендацією щодо довжини
```

Для розробника схема дає типи й помилки збірки/валідації. Для агента вона описує, які поля існують і як їх змінювати. Для адмінки вона визначає форму. Документація схеми версіонується разом із кодом; старі записи мігруються при зміні форми даних.

## Astro та майбутні секції

Сторінки першої версії використовують шаблони Astro з визначеним у коді порядком секцій. Прості літерали секцій виявляються автоматично; списки й інший структурований контент керуються схемою; редаговані параметри компонентів оголошуються в коді компонента. Пізніший конструктор потребуватиме явного реєстру: ключ типу секції, Astro-компонент, версія, дозволені поля й варіанти, назва та мініатюра. Сторінка конструктора міститиме впорядкований список екземплярів секцій зі стабільними ID. Саме сканування `.astro` файлів не може визначити дозволені значення, вкладені блоки й правила UX. Контракт автоматичної надбудови описано [окремо](CMS_CODE_FIRST_ARCHITECTURE.md).

Реєстр конструктора зараз не реалізуємо. Стабільні ID, схема полів і відокремлення контенту від верстки дозволяють додати його пізніше.

## Зв'язок медіа з контентом

Медіа зберігаються як окремі об'єкти. При заміні зображення старий файл не видаляється автоматично, поки на нього посилається історія або інший запис. Перед публікацією й відновленням перевіряємо доступність медіа. Оптимізація зображень залежить від призначення: іконка, картка, обкладинка та повноекранне фото мають різні вимоги. Обмеження завантаження перевіряються на сервері.
