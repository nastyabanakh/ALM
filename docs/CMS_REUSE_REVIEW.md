# Повторне використання BW CMS: стан і рекомендований напрям

Огляд коду від 29 жовтня 2026 року. Це оцінка поточної реалізації та пропозиція розвитку; пакет, інсталятор і віддалений деплой нижче ще не реалізовані.

## Висновок

CMS має корисну основу для повторного використання: спільні UI-компоненти й токени, файловий контент, перевірку схем, чернетки, контроль ревізій, спільний Publish і recovery snapshots. Проте зараз це CMS усередині ALM, а не незалежний продукт. Копіювання однієї папки не підключить її до іншого сайту. Для поточного Astro-проєкту поділ за відповідальністю зрозумілий; для багатьох клієнтських сайтів потрібне відокремлення клієнтської конфігурації та випусків CMS.

Це огляд коду, а не підтвердження безпомилкової роботи чи завершений аудит безпеки. Автоматичні тести не запускалися відповідно до чинних правил проєкту.

## Що де знаходиться зараз

| `public/admin/` | Інтерфейс, дизайн-система, UI Kit, preview runtimes, іконки |

| `astro.config.mjs` | Реєстрація локальної інтеграції |

| `src/content/` | Опубліковані дані конкретного клієнта |
| `src/layouts/BaseLayout.astro` | Зв'язок сайту з CMS: метадані, Const, runtime scripts і налаштування |
| `src/pages/` | Вхід до адмінки, redirect `/cms`, публічні шаблони колекцій |
| `src/sections/`, `src/components/` | Компоненти сайту з CMS-прив'язками |
| `src/styles/cms-rich.css` | Публічний вигляд rich content |
| `public/cms/slug.mjs` | Спільні утиліти slug, які також імпортує сервер |

| `.cms/` | Локальні чернетки, історія, staged files та recovery snapshots; ігнорується Git |
| `admin/` | Старий demo і локальний README; це не весь модуль адмінки |
| `templates/` | Загальний starter сайту; це не інсталятор CMS |

Зовнішні `.qa-admin-audit-20261028/`, `.playwright-mcp/` та звіти в робочій папці є допоміжними матеріалами, а не джерелом CMS. Не використовувати QA sandbox як версію для клієнтів. Не видаляти допоміжні матеріали чи `public/_astro/` без окремої перевірки використань. Чернетки та резервні копії в `.cms/` потребують окремої політики збереження: Git їх не резервує.

## Конкретні перешкоди для перенесення

1. `cms/model.mjs`: `pages` вимагає `HOME_PAGE_ID`, slug `home`, template `alm-home`; `homeContent` містить поля ALM (`hero`, `startingPoints`, `featuredHome`, contacts тощо). Новий сайт має відповідати чужій схемі або змінювати ядро.
2. `public/admin/index.html`: присутні міграції старих телефонів та ALM email. Їх треба перенести в явні версіоновані міграції конкретного сайту, а не переносити всім клієнтам як поведінку входу.
3. `api/admin.js`: є резервне значення GitHub repository `nastyabanakh/ALM`. Локальна інтеграція примусово вмикає локальний режим, але для універсального пакета потрібна явна конфігурація без клієнтського fallback.
4. `cms/project-workspace.mjs`, `src/content.config.ts` та інші модулі знають колекції `pages/posts/projects` і головний запис. Конфігурація має визначати колекції й кореневі налаштування проєкту.
5. Серверні модулі імпортують моделі з `public/admin/` та `public/cms/`. Спільні чисті моделі слід виділити в shared-шар пакета, незалежний від DOM та розміщення public-файлів.
6. `public/admin/index.html` містить близько 2400 рядків і значну частину orchestration. Варто поступово виділити state/history, API client, navigation та inspector у модулі. Сам розмір файла не доводить наявності багів.
7. Деякі документи описують попередні етапи: окремий `/cms`, окрему публікацію, старі обмеження колекцій/Const. Код уже перенаправляє `/cms` у `/admin/#cms`. Потрібен один актуальний integration guide з позначеними версіями.
8. Зберігання прив'язане до `process.cwd()` і локального запису файлів; блокування публікації реалізоване чергою всередині процесу. Перенесення в окремий пакет потребує явного project root. Для кількох серверних процесів потрібен спільний механізм блокування; поточна черга не є розподіленим lock.

## Рекомендована ціль

Окремий репозиторій BW CMS з одним пакетом для старту, умовна назва `@bw/cms` (пакет ще не існує). Усередині: core, shared, admin UI, Astro integration, adapters, migrations, CLI та docs. Не потрібно одразу розділяти кожен шар на окремий npm-пакет.

Клієнтський сайт зберігає власні `cms.config.*`, схеми/колекції, контент, компоненти, assets, прив'язки та секрети. Пакет постачає однакову версію CMS усім сайтам; особливості клієнта задаються конфігурацією й дозволеними extension points. Код у `node_modules` не редагують.

У майбутній конфігурації явно задавати project root, content/assets roots, site identity, schemas, routes/templates, кореневі налаштування, auth/storage/deployment adapters. Розділити глобальні налаштування сайту та запис головної сторінки, зберігши чинні Const через міграцію.

Astro integration має підключати маршрути/API/preview та стилі в контрольований спосіб. Ізоляція адмінки від стилів клієнтського сайту й preview у iframe мають залишитися частиною контракту. Підтримку іншого фреймворку додавати окремим адаптером після стабілізації Astro.

## Де працюватиме клієнтська адмінка

Сьогодні робочий шлях — локальний Astro dev server. Статичний хостинг сам по собі не дає серверу авторизації, persistent drafts або можливості записувати вихідні файли. Наявність `api/` не означає, що весь цикл редагування й публікації готовий на віддаленому хостингу: API явно блокує частину віддалених операцій.

Для клієнтського використання рекомендований наступний крок — окремий захищений CMS backend/worker з persistent workspace для кожного сайту та адаптером Git/deploy. Він приймає draft, перевіряє зміни, публікує їх у репозиторій сайту, запускає build/deploy і показує результат. Preview повинен рендерити draft на сервері/у preview workspace; статичний сайт не має сам змінювати джерела. Потрібні обмежені права, backups і відновлення. Спочатку окреме середовище на клієнта простіше ізолювати, ніж будувати спільний multi-tenant SaaS.

Розрізняти: збережено в draft → застосовано до source → deployed. Помилка deployment не повинна показувати успішне оновлення live-сайту.

## Оновлення

- Випускати версії CMS із changelog: patch для сумісних виправлень, minor для сумісних можливостей, major для несумісних змін. Довідка: https://docs.npmjs.com/about-semantic-versioning/.
- Фіксувати обрану версію CMS і lockfile у кожному сайті. Піднімати версію окремою зміною з переглядом; не підміняти live CMS глобальним latest bundle.
- Окремо версіонувати формати контенту/чернеток і контракт адаптера. Оновлення пакета не є автоматично міграцією даних.
- Міграції: preflight, dry run/звіт, backup, перевірка версії, застосування під lock, валідація, перевірний шлях відновлення. Повторний запуск не має повторно змінювати дані.
- Перевіряти сумісність і pending drafts до оновлення. Відкат пакета після зміни формату даних може вимагати відновлення snapshot.
- Спочатку оновлювати еталонні сайти/staging, потім одного клієнта, потім решту. Зберігати реєстр сайт → CMS version → schema version → deployment status.

## Інструкція агенту: що є і чого бракує

Вже є `AGENTS.md`, `docs/CMS_CONTENT_STANDARD.md`, `docs/CMS_FIELD_ARCHITECTURE.md` та `docs/CMS_SITE_PREPARATION.md`. Це корисні правила й контракти, але не завершена універсальна інструкція встановлення. `CMS_SITE_PREPARATION.md` переважно описує Const і має застарілі обмеження. До відокремлення пакета не називати копіювання поточних файлів готовим install workflow.

Поточна безпечна послідовність роботи агента над інтеграцією:

1. Зафіксувати базовий стан і зберегти існуючі зміни; визначити Astro/Node versions, routes, collections, media paths і майбутній спосіб хостингу.
2. Прочитати `AGENTS.md`, стандарт контенту й каталог полів. Визначити конфлікти схеми ALM з даними нового сайту до копіювання.
3. Скласти карту всіх залежностей із таблиці вище. Не копіювати контент ALM, assets, `.env.local`, `.cms`, QA copies чи demo як дані іншого клієнта.
4. Винести клієнтські схеми, branding, repository та міграції з ядра; не маскувати несумісність порожніми ALM-полями. Не переписувати BaseLayout іншого сайту цілком: переносити лише потрібні інтеграційні точки.
5. Створити власні секрети й контент, підключити loaders, metadata, rich renderer та стабільні `data-cms-*` bindings; технічні обчислювані елементи виключити через `data-cms-technical`.
6. Перевірити збереження identity записів, Const, посилань, source/alt media grouping, shared draft/history/Publish і recovery. Чинну заборону на запуск тестів у цьому проєкті зберігати до нового дозволу користувача.
7. Документувати підтримуване середовище та фактичний стан deploy/preview. Не обіцяти production-ready підключення, якщо доступний тільки local mode.

Після появи пакета потрібен окремий версіонований integration guide та переносимий agent skill з прикладами конфігурації, contract checks і діагностикою. Локальні `AGENTS.md` клієнта мають посилатися на нього, а не містити довгу копію внутрішніх правил ALM.

## Як зменшити помилки підключення

Нуль багів гарантувати неможливо. Запобігання — вузький документований контракт, явні bindings, незалежні client schemas, fail-fast config validation та перевірки поведінки на різних сайтах.

Перед масовим використанням потрібні щонайменше два незалежні Astro fixtures: мінімальний сайт без ALM-полів і сайт з іншими колекціями/структурою. На етапі автоматизації перевіряти build без CMS preview, недоступність запису без auth, draft/reload/Undo/Redo, одночасні зміни та конфлікти, Publish/Discard, rollback при помилці, references/slug/archive, media rename з усіма використаннями й міграцію з попередньої версії. Це план майбутніх перевірок, а не твердження, що вони виконані.

## Порядок робіт

1. Спершу відокремити ALM schema/config/migrations від reusable core і узгодити документацію.
2. Винести CMS у пакет та довести підключення на другому незалежному Astro-сайті.
3. Додати installer/doctor, CI contracts, версії, міграції та випуск першої перевіреної версії.
4. Реалізувати й перевірити production backend + Git/deploy adapter, persistent drafts і preview.
5. Налаштувати контрольоване оновлення клієнтських сайтів.

Масове переміщення файлів у цьому огляді не виконувалось: воно змінює багато import/source-rewrite шляхів і потребує окремого етапу реалізації та перевірки.
