# Єдиний стандарт контенту Astro-сайту

## Джерело даних

Редаговані значення сторінки зберігаються в одному записі `src/content/pages/<id>.json`. Кожна секція має стабільний ключ у `content.sections`; повторювані елементи є масивами цього запису. Метадані сторінки живуть у тому самому записі, а файли зображень і відео — у `public/assets`.

Astro-компоненти визначають структуру, стилі й поведінку. Вони отримують `content` як параметр і рендерять значення безпосередньо з запису. Адмінка змінює той самий запис через чернетку. Тому редагування JSON у редакторі коду та редагування в адмінці мають одне джерело значень. Відкриття `.astro` для редагування дизайну лишається звичайною частиною роботи.

## Прив’язка адмінки

Корінь секції має `data-cms-section="sectionKey"`; текстові елементи мають `data-cms-path="sections.sectionKey.field"`, атрибути — `data-cms-path-src`, `data-cms-path-href` тощо. Ключ записано в розмітці, тому переміщення елемента в DOM не змінює поле. Адмінка читає ці прив’язки з прев’ю й будує поля автоматично. Складні компоненти передають ключі до своїх видимих елементів через параметри `cmsTextPath` та `cmsHrefPath` або аналогічний контракт.

Поля інспектора беруться з фактичних DOM-прив’язок. Приховані слайди й стани також повинні мати прив’язки до запису, якому вони належать. Медіа вибираються з Media.

## Спільні змінні Const

Дані, які мають оновлюватися одночасно в кількох місцях, живуть у `content.consts` того самого запису. Інші поля зберігають посилання `{{const.key}}` як окремі фрагменти тексту, наприклад `Call us: {{const.companyPhone}}`. В одному полі може бути кілька посилань; для телефону в посиланні використовується `{{const.key|tel}}`, для email — `{{const.key|mailto}}`. Ключ стабільний, а назву, тип і значення можна редагувати в окремій вкладці **Const**. Під час публікації схема відхиляє посилання на неіснуючий ключ або невідповідний формат.

У редакторі таке поле показує фактичне значення й активну іконку змінної всередині інпута справа. У прев’ю іконка з’являється при наведенні; подвійний клік веде до спільного значення, де видно кількість використань. Чернетка оновлює всі використання одразу, публічний сайт — після публікації. Поля посилань мають тип і режим відкриття; Page та Page section використовують автоматичні прив’язки до маршруту сторінки й `id` секції. Точний контракт описано в [підготовці Astro-сайту](CMS_SITE_PREPARATION.md).

## Підключення нового Astro-проєкту

1. Агент знаходить редаговані тексти, посилання, медіа й повторювані дані; переносить їх у записи сторінок. Самостійно простежує всі використання одного логічного запису: фон, мініатюру, активний заголовок, мобільний варіант, приховані стани та дані контролера. Ці відображення підключає до спільної CMS колекції та того самого поля запису.
2. Компоненти отримують `content` і читають значення за стабільними ключами. Видимі поля отримують `data-cms-path`.
3. Схеми перевіряють структуру запису перед публікацією. Для спеціальних компонентів параметри й типи визначаються в коді компонента.
4. Після міграції новий текст додається до запису сторінки, а не дублюється літералом у `.astro`.

Без первинного перенесення довільний Astro-проєкт не можна безпомилково редагувати з універсальної адмінки: сам код не позначає, які рядки є контентом, а які належать логіці чи інтерфейсу.

## Поточний ALM

Головна сторінка перенесена на цей стандарт. Її попередні `staticText`-правки перенесено в поля запису. Записи статей і портфоліо залишаються окремими Astro Content Collections; роботу над їхнім редактором відкладено за [планом](CMS_ROADMAP_EXPANSION.md). Інші статичні маршрути й повністю багаторазове пакування ядра — наступні етапи.


## Компоненти та повторюваний контент у редакторі

Редактор секції показує картки елементів. Поля тексту, посилання та медіа одного компонента відкриваються разом після вибору картки або кліку на canvas. Корінь багаторазового компонента позначається `data-cms-component="Main button"`; вкладені поля зберігають свої `data-cms-path-*`. Кнопки й посилання без явної позначки групуються за найближчим `a` або `button`. Зображення мають окрему картку з вибором заміни й описом, коли опис доступний. Зелена рамка позначає компонент, синя — медіа.

Вкладка **CMS** у редакторі сторінки знаходить масиви об’єктів у записі контенту: FAQ, етапи, картки, характеристики, навігацію тощо. Вона показує колекції, список карток записів, пошук і окрему форму вибраного запису. У секції повторювані поля не виводяться суцільною формою: картка колекції веде до CMS. Клік на пов’язаний елемент на canvas відкриває відповідний запис. Порядок записів змінюється перетягуванням за лівий хендл з видимим місцем вставки (або клавішами вгору/вниз на хендлі), зберігається порядком масиву в тій самій чернетці та підтримує Undo/Redo. Link overrides з індексними шляхами переміщуються разом із записом.

### Як агент визначає колекцію

1. Знайти в коді `.map(...)`, повторювані FAQ/accordion items, картки, слайди, етапи й списки характеристик з однаковою структурою полів. Перевірити їхнє призначення: схожий CSS сам собою не доводить, що це одна колекція.
2. Дані кожного списку зберігати масивом об’єктів в одному записі. Для спільного між сторінками контенту створювати окрему Astro Content Collection і явні посилання на записи; вкладка колекцій сторінки наразі працює з масивами поточного запису. Статті та портфоліо залишаються доступними через посилання у вкладці CMS.
3. Для рендерингу передавати індекс у стабільні шляхи кожного поля: наприклад, `faq.0.question`, `faq.0.answer`. Корінь списку позначати `data-cms-collection="faq"`, необов’язкову читабельну назву — `data-cms-collection-label="FAQ"`, корінь картки — `data-cms-item={index}`. FAQ вже використовує цей контракт. Не об’єднувати різні списки лише тому, що вони знаходяться в одній секції.
4. Ідентифікатори записів, якщо вони є, мають залишатися незмінними при перестановці. Поточний редактор змінює порядок масиву без зміни вмісту записів. Залежні посилання й поля компонента мають належати запису, а не окремому дубльованому масиву.
5. Повторюваний контент редагувати у формі запису CMS. Подвійний клік по його тексту на canvas відкриває запис замість inline-редагування. Структура й оформлення картки залишаються в Astro-компоненті.

Поточна вкладка підтримує редагування та перестановку наявних записів. Створення/видалення записів, схеми колекцій, міжсторінкові references та фільтри списків потребують окремого розширення моделі й рендерингу; їх не слід вважати реалізованими лише через наявність вкладки CMS.

Колекції на canvas отримують фіолетову рамку й кнопку-мітку CMS. Явний `data-cms-collection` визначає межі списку; без нього редактор знаходить спільний DOM-контейнер полів з однаковим шляхом масиву. Для точних меж агент має завжди ставити явний атрибут на корінь списку.


## Спільний запис для кількох відображень: обов’язок агента під час підключення

Агент визначає належність за логікою компонента й потоками даних, а не лише за сусідством у DOM. Користувач не повинен вручну пояснювати, що мініатюра й відповідний фон слайдера є двома відображеннями одного слайда. Однаковий URL зображення сам собою не є підставою об’єднувати незалежні колекції.

Для слайдера створюється одна колекція записів. Наприклад, `sections.finishedStandard.showcaseItems[index].image` використовується і фоновим зображенням, і мініатюрою. Копій поля на кшталт `backgroundImages[index]` або `thumbnailImages[index]` не створювати, якщо за задумом це те саме фото. Зміна одного поля запису має оновити всі його відображення і в чернетці, і після публікації.

- Корінь усієї взаємодії отримує `data-cms-collection`. Рознесені DOM-фрагменти одного запису, зокрема фон і картка навігації, отримують однаковий `data-cms-item={index}` у межах цієї колекції.
- Усі використання фото отримують однаковий `data-cms-path-src`. Атрибути, які читає JavaScript (`data-title`, `data-desc` тощо), теж отримують відповідні `data-cms-path-data-title`, `data-cms-path-data-desc`.
- Спільний активний заголовок/опис повинен перемикати шлях прив’язки разом з активним записом. Не залишати постійний шлях `.0.title`, коли на екрані інший слайд. Після зміни шляхів контролер надсилає локальну подію `cms-bindings-refresh`; редактор оновлює прив’язки й належність до запису.
- У редакторі відкриття CMS item надсилає `CMS_SELECT_RECORD` із ключем колекції та індексом запису. Контролер показує цей запис. Автоперемикання в редакторі не повинне відводити користувача від запису, який він редагує.
- Повторні DOM-відображення одного поля не створюють незалежних копій контенту. Порожній декоративний `alt` не повинен ставати окремою карткою Image в параметрах секції.

Це аналіз і підключення, які агент виконує під час міграції конкретного сайту. Редактор далі читає явний контракт прив’язок; він не повинен намагатися вгадати семантичні зв’язки за зовнішньою схожістю зображень у браузері.


## Const як фрагмент тексту

Поля параметрів відображають посилання на Const як невідокремлювані фіолетові мітки з поточним значенням і спільною іконкою Const. Звичайний текст до/після мітки залишається редагованим. Insert Const вставляє мітку в збережену позицію курсора або замінює тільки виділений фрагмент. Backspace/Delete поряд із міткою видаляє всю мітку, не змінюючи саму константу. Подвійний клік по мітці відкриває її спільне значення. Копіювання й вставка зберігають посилання, а не перетворюють його на поточне значення.

У JSON зберігаються текст і токени `{{const.key}}`, без HTML редактора. Прев’ю й опублікований сайт підставляють усі токени всередині рядка. Перевірка перед публікацією знаходить невідомі ключі й неправильний формат кожного посилання, включно з посиланнями всередині змішаного тексту. Наявні поля з одним токеном підтримуються без міграції. Поля власного HTML/JS-коду залишаються звичайними редакторами коду без вставок Const.


## Чернетка медіа та публікація файлів

Код і фізичні файли — джерело істини для опублікованого сайту. Media редагує збережений план у `.cms/media-draft/state.json`; Спільний проєктний Undo/Redo повертає кроки контенту й медіаплану в порядку внесення незалежно від вкладки. Перезавантаження вкладки не губить чернетку. Кожна зміна перевіряє ревізію, щоб вкладки не перезаписували одна одну.

Назва в Media означає майбутню фізичну назву. До публікації панель показує Draft path і Published path. Перейменування, переміщення, папки, видалення, завантаження, заміна файла та alt зберігаються в чернетці. Нові/замінені бінарні файли живуть у `.cms/media-draft/files`, а авторизований preview endpoint підтримує відеодіапазони. Прев’ю редактора використовує ці файли, публічний сайт — опубліковані.

Єдиний проєктний Publish застосовує план до `public/assets` і переписує відомі використання у джерелах, контенті та активних чернетках. Це одна операція з публікацією всіх чернеток сторінок, статей і портфоліо після перевірки ревізій та схем. Окремих Publish media / Publish entry немає. Фізичні файли перевіряються на зовнішні зміни, конфлікти шляхів та відомі використання; старі ревізії й неоднозначні обчислювані URL блокують операцію. Зберігаються резервні копії змінених джерел та медіа, помилки запускають відкат. Після публікації починається нова базова версія.

Використані файли не видаляються без явної заміни/прибирання прив’язок. Discard нового завантаження теж не повинен залишати на нього посилання в чернетках контенту. Точкові перейменування не приховуються симлінками або дубльованими файлами. Каталог опублікованих медіа зберігає допоміжні метадані; його організація після публікації відповідає диску.

## Відео

`video.poster` та `source.src` мають явні CMS-шляхи. Інспектор показує справжній `<video controls>`, поточний URL, стан завантаження та помилку; для вибору джерела використовується Replace video, для постера — Replace poster. Після зміни URL оновлюються MIME type та video.load(). Незмінене відео не перезапускається від редагування сусіднього тексту. Порожні дочірні панелі повертають DocumentFragment, щоб DOM не виводив слово null.


## Межі CMS item та групування зображень

Не розширювати inferred item до предків, що містять статичний контент секції. Власний індексний шлях поля або явна пара data-cms-collection/data-cms-item визначають належність. Автовизначення допускає лише найменший однозначний контейнер без статичних полів та інших записів. Якщо таких доказів немає, поле лишається в секції.

Динамічні спільні в’ю (слайдери, scroll steps) синхронізують активний індекс, indexed paths та component descriptor. Відкриття запису у CMS фіксує відповідний крок до виходу з колекції.

Кожне зображення має одну медіагрупу для source і alt/description. Правило однакове для секцій і CMS items. Для кількох відображень одного source групування відбувається за прив’язкою джерела, з описами всередині цієї ж групи. Індивідуальні decorative alt поля відрізняються підписом, а не окремою текстовою карткою. Не відкидати повторний DOM binding до визначення його власника.


## Спільна історія й атомарна публікація проєкту

Усі вкладки — в’ю одного draft. Undo/Redo використовує єдину хронологічну чергу з типами content, entry-content і media-draft; зміна вкладки не змінює ціль скасування. Поля CMS-записів, завантаження медіа з редактора запису та зміни Media входять у ту саму історію. Перед відкриттям підтвердження Publish усі відкриті форми зберігаються в чернетки.

Сервер збирає всі записи з чернетками, валідує їх і конфлікти адрес, перевіряє ревізії, створює резервний стан у `.cms/project-publications` і застосовує медіаплан та всі записи під спільним блокуванням. Помилка наступного кроку повертає джерела, активні файли, історію записів і медіачернетку до стану перед публікацією. Успішна публікація створює нову базову версію й очищає сесійний Undo/Redo.

## Надійність робочого простору та доступу

Після успішного Publish відповідь містить новий published baseline, список сторінок, стан Media і опубліковані CMS entries. Оновлення preview не змінює результату вже виконаної публікації. Повторні мережеві запити дозволені автоматично лише для читання.

Історія Undo/Redo зберігається у браузері окремо для користувача та відновлюється після reload лише при збігу published baseline, контенту, Media revision і CMS entry revisions. При недоступному/переповненому сховищі редактор явно попереджає. Після Publish починається нова історія. Код та файли сайту залишаються джерелом published значень; browser history не змінює їх самостійно.

CMS Pages підтримують inline Const для редагованого контенту та медіаописів. Стабільні ID, slug і дата зберігають свої типи. Обкладинка і кожне зображення gallery містять source та description в одному блоці. Константи перевіряються також у published entries, які не мають власних draft, щоб видалення спільного ключа не ламало ці сторінки.

Стан відкликаних сесій та throttle зберігається в `.cms/security`, поза public. Поточна реалізація розрахована на один локальний API process. Для кількох API instances потрібне центральне транзакційне сховище сесій/throttle; проста спільна директорія або ephemeral serverless storage не забезпечує атомарності між instances. `CMS_TRUSTED_ORIGINS` — необов’язковий список додаткових точних origins через кому; за замовчуванням дозволено origin самого запиту. `CMS_TRUST_PROXY=1` дозволяє довіряти перезаписаному reverse proxy заголовку протоколу; вмикати лише за довіреним proxy.

Абсолютні URL сторонніх серверів не є локальними asset references, навіть якщо шлях після домену збігається з `/assets/...`. Для власного публічного домену можна задати `CMS_SITE_ORIGIN=https://example.com` (або список origins через кому): лише ці абсолютні URL переписуються разом із локальними root-relative/relative references. Те саме визначення власника використовується для захисту від видалення використаних файлів.

## Глобальна область Const

Усі Const визначаються на рівні проєкту в `content.consts`, а не в окремій сторінці чи CMS-записі. Будь-яка сторінка, компоненти, налаштування сторінок і записи колекцій використовують спільні `{{const.key}}` посилання. Зміна визначення поширюється на всі зв’язані поля сайту через спільну чернетку та Publish. Не створювати page-local копії визначень.

## Технічні / обчислювані елементи

Використовувати `data-cms-technical="причина"` на найменшому спільному контейнері обчислюваного UI, наприклад `<div data-cms-technical="slider-counter">…</div>`. Усі нащадки виключаються з явних і автоматичних CMS-прив’язок, структури, hover і inline editing. Усередині не додавати editable data-cms-path/data-cms-instance. Це контракт для похідних значень (поточний індекс, загальна кількість, pagination/progress/status), а не спосіб приховати авторський текст. Текст картки чи її номер лишається редагованим, якщо є авторським контентом.

Starting Points: current = active index + 1, total = кількість карток; форматування й aria-label створює код. Лічильник більше не читає sections.startingPoints.counterCurrent/counterTotal. Старі значення контенту не видаляються з робочих чернеток, але більше не керують цим UI.

### Configurable collection fields

Collection definitions live in the home content's `editorSettings.collectionSchemas[scope]`, with `scope` set to `content:<path>` for inline lists or `page:posts` / `page:projects` for page entries. Fields have stable `id` and `key`, a type, group and order. Custom fields use `custom.<id>` inside each item; rich documents use `richText[<field key>]` alongside a legacy plain-text mirror. Removing a field from layout preserves item data for Undo/recovery. A rename changes the display name, not the source path.

References store the target record ID, multireferences an ordered array of unique target IDs. They never copy the target title. Resolve the title and public URL from the current target collection when displaying it. Exclude archived/deleted targets; reject missing or invalid targets before the shared project Publish. New inline reference targets receive persistent IDs in the project draft. Public rich text uses the allowlisted block renderer and escaped text/URLs, never raw authored HTML.
